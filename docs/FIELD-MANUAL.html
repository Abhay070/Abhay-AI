§1What it is

Praxis is a complete assistant — web interface, agent loop, tools, memory, streaming — that runs on your machine and talks to whichever model you point it at. It is not a model. It is everything around one.

That distinction is the whole design. Models turn over every few months; the product around them does not have to. Swapping the brain is a one-line change in .env, because no application code knows which backend is answering.

What Praxis adds that a raw API call does not: a compiled identity that survives every turn, ten working modes with promises that are mechanically enforced, a constraint checker that catches what a model provably cannot check about its own output, a tool protocol that works on every backend including local ones, and a refusal to ever present a failure as a success.

The governing rule

Three ways to fail, held equally bad: hallucination (confidently false), paralysis (refusing to help because it cannot guarantee perfection), and false confidence (a definitive answer on weak evidence). Most assistants guard only against the first and become useless in the second way while congratulating themselves. Praxis attacks all three — and a blank reply that reports success is the worst case of all, because the user cannot even tell something went wrong.

§2Lifecycle of a turn

One user message, end to end. Everything is emitted as typed events over Server-Sent Events, so the interface can show what the assistant is doing rather than an opaque pause.

POST /api/chat  { message, mode, strategy, attachments[] }
  │
  ├─ store      user turn saved; attachments kept by reference, never inlined
  ├─ resolve    provider health-checked; falls down FALLBACK_CHAIN if dead
  ├─ compose    identity + mode overlay + memories + tool list + fitted history
  │                  ↳ tool list compacts if it would eat the budget   (§5)
  │                  ↳ attachment text folded in here, capped, with a read_file pointer
  ├─ detect     constraints stated in the request  → 14 kinds  (§7)
  │
  ├─ generate   ── stream ──▶ token events
  │     ↳ <tool_call> seen? hold the text back, run it, feed the result, continue  (§8)
  │     ↳ HTTP 429?    wait what the provider asked, drop oldest turns, retry  (§9)
  │     ↳ no content?  raise EmptyAnswer naming the cause — never return ""     (§9)
  │
  ├─ verify     constraints checked mechanically; mode contract checked  (§6, §7)
  │     ↳ broken? hand the model its specific defect and regenerate (up to 2×)
  │     ↳ still broken after 3 tries? append the failure to the answer and say so
  │
  └─ done       message id, elapsed, tool rounds, attempts, token estimate

§4The system prompt

Assembled fresh every request from four parts, in this order:

Core identity
~1,170 tokens. Always present. The operating philosophy — verify premises before answering them, read tone before drafting a reply, obey a stated constraint exactly or say plainly that you cannot, calibrate refusals to actual harm rather than to keywords.
Context
Current date and time, the training-cutoff caveat, and the user's name.
Memory
Up to twelve recalled facts, chosen by keyword overlap with the recent conversation. Omitted entirely when nothing scores.
Tool protocol
The <tool_call> grammar plus the enabled tools. ~700 tokens in full, ~250 compacted.
Mode overlay
531–1,091 characters, and never trimmed. A mode that loses its overlay is not a mode.

Compiling it rather than pasting a specification is what makes it affordable: the raw philosophy document runs to roughly 4,000 tokens, and this carries the same behaviour in under half that.

GET /api/prompt?mode=direct returns exactly what would be sent. When a mode appears to do nothing, that endpoint settles it in one request.

§5Token budget

The conversation is resent in full on every turn, so cost grows with the chat rather than with the message. Free tiers meter this per minute — Groq's on-demand tier allows 8,000 tokens a minute, prompt included — which is why a long chat with a thinking model starts refusing requests that a short chat served fine.

MAX_PROMPT_TOKENS
4,000. The real budget. Counting turns says nothing about their size — twenty short turns and twenty turns each carrying a PDF are the same number and wildly different prompts.
Fresh-chat cost
~1,713 tokens, of which ~1,705 is the system prompt and its tool list.
Tool-list compaction
Automatic when the full list would exceed 15% of the budget. Drops the worked examples, keeps every tool name and argument — about 450 tokens off every request.
ATTACHMENT_CHARS
5,000 characters of a file ride in the prompt; the rest stays on disk behind read_file.
MIN_QUESTION_CHARS
1,200. However tight the budget, the question is never trimmed below this. A prompt trimmed past it is not a cheaper request, it is a wasted one.
Under pressure
Oldest turns go first; the newest user turn and everything after it is never dropped. On a 429, each retry drops half the remaining history, so the retry is genuinely cheaper than the try that was refused.

§6Modes and contracts

A mode is a promise. Prompt text alone does not keep one: a model reads "under 150 words" as a suggestion and writes 400, and the mode silently becomes decoration — the label says Direct, the answer reads like Standard, and nothing tells the user which they got.

So every promise that can be checked mechanically, is. A broken contract feeds the same repair loop as a broken constraint: the model is told exactly which promise it broke and rewrites.

ModePurposeEnforced promise
◈ standardBalanced; adapts to what you bring— none, deliberately
→ directMaximum signal, no cushioningunder 150 words · no throat-clearing opener
▲ founderCommercial pressure-testingends with something testable this week
⊗ realityStructured teardown with a verdictstates one of PURSUE / PURSUE WITH CHANGES / TEST FIRST / DROP IT
⚒ buildIdea to executable projectships code or commands, not advice about them
◎ teacherUnderstanding from the ground upasks a real question · never says "as you probably know"
? socraticGuides rather than tellsends on a question
✓ examTests you and marks youasks a question
◇ researchSources, cross-checks, dated claimscloses with established / contested / unknown
▤ briefDecision-shapedfive named headings · under 350 words

Two rules govern what may become a contract, because a false accusation is worse than a missed one: only promises the mode's own prompt actually states, and only checks that cannot reasonably misfire on a good answer. Word limits carry a 1.25× tolerance — failing an answer at 151 words is pedantry that costs a whole regeneration.

scripts/compare_modes.py "your question" asks one question in every mode and reports what each promised, whether it kept it, and the shape of what came back — and says plainly when two modes answer identically, which is the failure worth catching.

§7Constraint engine

Asked for four sentences with no letter E or S, a model produced fifteen Es, sixteen Ss, and invented words like trnspnds trying. Asked for descriptions of exactly eight words, it produced seven, seven and six.

No amount of prompt text fixes that. Generation is token-level — a token is commonly several characters, chosen by a model with no per-letter counting step — so "be careful to obey the constraint" is an instruction the model cannot execute. It complies approximately and reports full compliance, which is the worst of both.

Code checks it in microseconds. Fourteen kinds are detected in the request and verified against the answer:

forbidden_lettersword_count sentence_countsentence_word_counts jsonbanned_words no_punctuationword_initial alternating_initialsabecedarian line_endingsword_per_line line_word_maxtable_cell_words

Detection is deliberately conservative and requires explicit constraint language. A missed constraint costs nothing — the answer is no worse than before. A falsely detected one wastes a generation and teaches the user that the checker is noise. Where a rule cannot be checked honestly — "use no nouns" needs a part-of-speech tagger — nothing is claimed.

The repair loop

A violation is handed back as a named defect, not as "try again":

Your previous answer broke constraints the user set. A checker ran over
it and found these specific failures:

- Must not contain the letter(s) 'e'. 'e' appears 4x. Offending words
  include: battery, generates, electrodes.

Rewrite the answer so it satisfies every constraint. Rules for the rewrite:
- Use only real words. Do not delete letters from words to dodge a letter
  rule — 'trnspnds' is not a word and does not count as a fix.
- If a constraint genuinely cannot be met with real language, say so
  plainly and explain why, rather than shipping something that violates it.

That converts an impossible task into an easy one: the model no longer has to count, it only has to repair a named fault. Two retries are allowed. If the answer still fails, Praxis appends the failure to the answer rather than passing it off as compliant:

What a failed check actually shows the user

Check failed after 3 attempts: word 1 starts with 'h', not 'a' (initials so far: hiacsatt). The answer above does not meet what you asked for.

§8Tools

Tool calls run on a text protocol — <tool_call>{"name": …, "args": {…}}</tool_call> — rather than a provider's native function-calling API. Native calling is better where it exists, but it exists differently on every provider and not at all on many local models. The text protocol works identically on Ollama, Groq, Gemini and a model you trained yourself last Tuesday, which is the point of the project.

The agent watches the stream for an opening tag and holds text back from the screen the moment one appears, so raw JSON never reaches the user. A partial <tool_ca at the tail of a chunk is held too.

ToolDoesDefault
calculateExact arithmetic — the model never computes it itselfon
current_timeDate and time, with timezone offseton
remember / recall / forgetDurable facts about the useron
web_search / web_fetchSearch, and read a page as texton
read_fileThe full text of an upload, past the excerpt in contexton
wikipedia / dictionary / exchangeEncyclopedia, definitions, currency at today's rateon
github_repo / hacker_news / arxivRepository facts, front page, preprint searchon
run_pythonExecutes model-written code on your machineoff

run_python is off by default and stays off unless you set ENABLE_CODE_EXEC=true. It executes code a model wrote, on your machine, with your files.

MAX_TOOL_ROUNDS=6 caps a single turn, so a confused model cannot spin forever burning tokens. A tool that raises returns an error to the model rather than taking down the request; an unknown tool name gets a list of the real ones.

Three things the streaming reader does that the textbook version does not

Reads reasoning
A thinking model streams its scratchpad in delta.reasoning and its answer in delta.content. The reasoning is counted but never shown — putting it on screen would present the scratchpad as the reply. Ignoring the field entirely meant that when thinking consumed the whole output budget, an empty string was stored and the interface showed a blank bubble with a tick beside it.
Refuses silence
A stream that yields no visible characters raises EmptyAnswer naming the cause and the setting that fixes it — "spent its entire 4096-token budget thinking and never started the answer. Set REASONING_EFFORT=low, or raise OPENAI_MAX_TOKENS." Ollama and Gemini get the same treatment for their own thinking fields and finish reasons.
Survives disagreement
"OpenAI-compatible" is a family resemblance, not a specification. An endpoint that rejects reasoning_effort or max_tokens with a 400 gets the parameter dropped and one silent retry. The user never learns the parameter exists.

Rate limits

A 429 is not a broken backend; it is a working one asking you to wait. Praxis waits the interval the provider named — Groq puts it in the message body, not only in the Retry-After header — and drops the oldest half of the history before retrying, because waiting alone cannot help a request that is larger than the whole minute's allowance. Up to three attempts, each narrated with a live countdown.

When waiting genuinely cannot help, the error names the three things that shrink a turn instead of saying "rate limited": start a new conversation, lower REASONING_EFFORT, or lower MAX_PROMPT_TOKENS — with the current turn's cost in tokens, so the advice is grounded.

Health checks

Health probes reach the network, cached 30 seconds. An earlier version only inspected configuration, so a port with nothing listening reported healthy and the council wasted a slot on it every turn. A health check that cannot fail is not a health check.

§10Strategies

single
One model. Streams token by token. The default.
race
Several models start; the first usable answer wins and the rest are cancelled. Costs latency of the fastest, not the slowest.
council
Several models answer in full; a judge picks the winner. Cannot stream — nothing can be shown until every member has finished — so the wait is narrated instead: who is running, what each returned, who won and why.
cascade
The cheap model answers first. Only if the answer looks weak does it escalate to the strong one. Most questions do not need the expensive model.

Judging uses a blind ballot: the judge sees answers labelled A, B, C and never learns which model produced which. Without that, a judge reliably prefers whichever name it recognises.

When no judge is reachable, a stated heuristic decides, and it prefers honest hedging over confident length — a member that says "I'm not certain" beats one that invents a detailed answer. Unreachable members are dropped with a reason shown in the interface, so listing a local model alongside hosted ones is safe: it simply sits out when the machine is off.

Measured, not assumed

The council runs genuinely in parallel over HTTP — three members cost 1.02× one member, verified against real servers with real latency. Against a CPU-bound local model it does not, and cannot: that path is GIL-bound, and threading it measured worse (three threads cost 6.41× one). The code says so where it matters rather than claiming a parallelism it does not have.

§11Memory

Facts are stored deliberately, by the model calling remember, not scraped from every turn. Recall scores by keyword overlap with the recent conversation, plus a small bonus for memories that have proved useful before, plus a standing bonus for preferences and goals.

No embeddings, no vector store. That is a considered choice: at personal scale — hundreds of memories, not millions — lexical overlap is roughly as accurate and has one decisive advantage. You can look at a recalled memory and understand why it surfaced. A memory system whose behaviour is inexplicable is one you stop trusting, and an untrusted memory is worse than none. Swap in embeddings past a few thousand; the interface does not change.

Everything is inspectable and editable from the memory drawer, and duplicates are collapsed on case and punctuation.

§12Storage and API

SQLite in WAL mode, one file at data/praxis.db. Five tables: conversations, messages, memories, files, settings. Messages carry a JSON meta blob — the mode, provider, strategy, tool rounds, constraint attempts, and any attachments the turn carried.

Attachments

Uploads are parsed to text at upload time and stored with an id. The id travels with the message; the text is folded into the prompt at compose time and never enters the transcript. A forty-page PDF is an attachment, not forty pages of the user's own message.

PDF extraction catches BaseException, not Exception — pypdf imports cryptography, whose Rust bindings raise pyo3's PanicException, which subclasses BaseException specifically so it dodges ordinary handlers. Catching only Exception returned a bare 500 with a Rust stack trace instead of a usable message.

§13Web client

One file, plain DOM, no framework and no build step. The app is small enough that a framework would cost more than it saves, and this way it can be read end to end.

Markdown is rendered by a small hand-written pass: everything is HTML-escaped before any markup is added, so model output can never inject into the page. Fenced code is pulled out first so its contents never meet the inline rules.

The visual system is derived from a G-SHOCK × Pokémon watch: a cool olive-grey ground, a hot red accent, an LCD-green for verified states, and hard geometry. Light and dark both defined at token level.

What the interface shows that a chat box does not

  • Tools running, with arguments and results, as they happen
  • The mode's promises as a chip, and a note when one was broken and rewritten
  • Council members thinking, each answer's preview, and the verdict with its reason
  • A live countdown when a rate limit is being waited out, and how many turns were dropped to fit
  • Attached files as chips on the turn that carried them
  • A token meter, a prompt inspector, a command palette, slash commands, and thirteen keyboard shortcuts

The fake model server

tests/fake_model_server.py is not a mock object. It is a real HTTP server, spoken to over a real socket by the real provider code, streaming real Server-Sent Events. The only thing it fakes is the intelligence.

That distinction decides what the tests can prove. Mocking Provider.stream proves the branching logic and nothing else — a mock returns instantly and never touches the network stack, so a "concurrency" assertion against one is meaningless. Here each server sleeps before answering, so parallelism is measured. It can also be told to 429 the first N requests Groq-style, to refuse parameters it does not know, or to reason forever and never write an answer.

The 100-question benchmark

Five sections of twenty: premise traps, logic and spatial traps, hard structural constraints, sarcasm and subtext, domain edge cases and refusal calibration. It separates two things a single score would blur:

Machinery
Praxis's own job, graded exactly. Did an answer arrive? Was it blank? Did the turn error? Did the mode keep its contract? Did constraint checking engage? A failure here is a bug in this repository.
Constraints
The twenty structural questions, graded character by character. Not an opinion.
Substance
Keyword-scored, and therefore crude — the report says so on every run. A keyword can pass an answer that names the right person and gets the rest wrong. The full transcript is written to disk for exactly this reason.

The grader is itself calibrated. Each of the nineteen mechanically checkable constraints has a hand-written answer that genuinely satisfies it and one that genuinely does not, and both directions are asserted — plus a check that praxis/constraints.py and the benchmark agree about every one, since they are independent implementations. Writing those compliant answers by hand is the point: a rule you cannot satisfy yourself is a rule you have no business scoring.

Current state, fake backend

100/100 questions answered. Zero machinery faults. Substance scores against a scripted backend are meaningless by construction — run python tests/benchmark.py with your own key for a real one.

§16Incident log

Every entry here was found in use or by adversarial testing, and each is now pinned by a test. Red is a failure the user saw; amber is one caught before they did.

Blank replies with no error anywhere

Symptom
An empty assistant bubble with a tick and "1.56s" beside it. No error, no explanation.
Mechanism
A reasoning model streams thinking in delta.reasoning and the answer in delta.content. The reader dropped the first and never checked the second arrived. When thinking used the whole budget, the stream closed cleanly and an empty string was stored as a success.
Fix
Providers count what they yield and raise EmptyAnswer naming the cause and the setting that fixes it. Same for Ollama and Gemini.

HTTP 429 on every other question

Symptom
TPM: Limit 8000, Used 4949 — repeatedly, with the "Used" figure well under the limit.
Mechanism
Each request cost 3–5k tokens: a 2,163-token system prompt plus the whole conversation resent, plus reasoning tokens. The second question in a minute did not fit.
Fix
Wait the interval the provider named, drop the oldest half of history each retry, cap what is resent, compact the tool list (−450 tokens/request), and when waiting cannot help, name the three things that shrink a turn.

The PDF pasted into the user's own message

Symptom
Attaching a file turned the user's message bubble into pages of extracted text, ending in "[excerpt only]".
Mechanism
The client appended the file's text to the message body before sending, so the transcript became the document.
Fix
Attachments travel as ids. The text is folded into the prompt at compose time; the turn shows a chip. read_file still reaches every word.

The question pushed out of its own prompt

Symptom
None visible — the model simply answered as though it had not read the question.
Mechanism
Budget trimming kept whatever it reached walking backwards, which is the last assistant turn when a history ends with one. A large attachment then pushed the user's question out.
Fix
Anchor on the newest user turn and everything after it; that block is never dropped, only abridged, and never below 1,200 characters.

The answer erased by its own failure note

Symptom
A mode that broke its promise three times showed only the failure note — the answer itself was gone.
Mechanism
The client cleared the message body on every mode_breach, including the final one, where no rewrite follows.
Fix
Only constraint_retry clears, because only it precedes a rewrite.

A failed turn showed nothing at all

Symptom
An error left the bubble blank for the whole turn.
Mechanism
The error event updated the model object but never touched the DOM.
Fix
Errors render immediately, in words that name the fix.

Health checks that could not fail

Mechanism
The check inspected configuration and never touched the network, so a dead port and a garbage key both reported healthy — and the council wasted a slot on them every turn.
Fix
Probe the endpoint, cache 30 seconds, distinguish unreachable from rejected-key from wrong-model.

The council ran sequentially

Mechanism
Three members cost 3.24× one. A synchronous forward pass was blocking the event loop.
Fix
HTTP backends were never affected — verified at 1.02×. Threading the local path made it worse (0.87s → 2.17s per token); the model is GIL-bound. Reverted, and documented with the measurements rather than left as a mystery.

False accusations from the constraint checker

Mechanism
Three separately: a markdown bullet counted as a word, so "every word starts with P" failed a correct list; a count scoped to a table column was applied to the whole answer; and a run of per-sentence counts took only its first number.
Fix
Words must contain a letter or digit; table_cell_words and sentence_word_counts became real constraint kinds. A false accusation costs a whole regeneration and teaches the user the checker is noise.

Recommended a text-to-speech model as a chat backend

Mechanism
list_models.py filtered on "tts", which canopylabs/orpheus does not contain, and its ranking fell through to name length.
Fix
Rank by stated parameter count and instruction-tuned markers, and penalise single-language and single-task models. A user-facing error, and mine.

If it answers nothing at all

Run the doctor first. In order, the usual causes are: PROVIDER=demo (a script, not a model — every mode will answer identically); a model name your account cannot reach; a key with no quotes and no spaces that is nonetheless not loaded because there is no .env; and a free tier's per-minute allowance, which Praxis now waits out and narrates rather than failing.

§18Limits

Stated plainly, because a specification that only lists strengths is marketing.

No authentication
There is no login and no per-user separation. Anyone who reaches the port gets the assistant, the conversations and the memories. Do not expose it publicly — not on a Codespaces public port, not behind a tunnel — until auth exists.
It is not the model
Praxis cannot make a weak model clever. It can stop a weak model lying about whether it obeyed you, and it can ask three models and take the best — that is the ceiling.
Keyword scoring is crude
Outside the constraint section, the benchmark probes for phrases. It can pass an answer that names the right person and gets the rest wrong. Read the transcript.
Some constraints are unenforceable
"Use no nouns" needs a part-of-speech tagger. Praxis reports it rather than pretending to check it.
Memory is lexical
Keyword overlap, not embeddings. Right at personal scale; swap it past a few thousand memories.
Token counts are estimates
Four characters per token holds well enough for English to be a useful gauge and badly enough that it is never presented as exact.
The council cannot stream
Nothing can be shown until every member has finished and the judge has ruled. The wait is narrated, not hidden.
Single machine, single user
SQLite, local files, no queue, no worker pool. That is the right shape for what this is, and the wrong shape for a service.

§19Philosophy, made mechanical

A principle stated in a prompt is a hope. A principle a checker enforces is a property. This is the set of behaviours the product now guarantees rather than requests, each pinned by a test that fails if it regresses.

Don't stall

An answer that stops at "I cannot confidently determine this" and leaves the user where they started is a failure here, held as costly as being wrong. praxis/momentum.py detects the stop — a signal that the question cannot be settled and no way forward — and repairs it through the same loop that repairs a broken constraint, so the answer keeps its honesty but gains the next step: what to check, what to measure, what to assume meanwhile. An honest answer that already moves ("I'd take Postgres, though verify the throughput") passes untouched, and a safety refusal is exempt in the checker itself — a repair loop that argues with a refusal is one that eventually gets a refusal overturned.

Don't crown a bad field

Three weak answers do not become one good answer by being compared. The council judge may now return NONE, the heuristic path checks the same thing so turning the judge off does not turn the honesty off with it, and the answer carries NO CONSENSUS — insufficient confidence above the best available answer, which is still shown. What it deliberately cannot catch is a confident fabrication among the candidates: detecting that a specific, assertive answer is false needs the ground truth the council does not have, and the code says so rather than pretending otherwise.

Two layers

Verification runs in the background. Normal view — the default — shows a quiet activity line (Thinking, Comparing the answers, Making sure it gives you a next step) and then the answer. Debug view shows every tool, check and verdict. The machinery is identical; the toggle only decides whether it is on screen, and the choice persists per browser. Things the user must see — the no-consensus label, a failed constraint — live in the answer itself and appear in both.

Outside content is data, never instructions

Tool results, fetched pages and uploaded files are fenced by praxis/untrusted.py with a boundary that states what they are and that they cannot give instructions — with the user winning any contradiction. The fence marker is random per request and stripped from the body, so content cannot close it and write outside. Text shaped like an attempt to give orders is flagged to the interface. None of this makes injection impossible, and the module says so; it removes the easy version and does it in one place.

Memory with provenance and supersession

Every memory records where it came from, a confidence, and whether the user confirmed it — a confirmed fact reads differently from a 70%-inferred guess. A changed preference retires the old one instead of both contradicting each other in the prompt forever: "I prefer dark mode now" supersedes "I prefer light mode", conservatively (same subject, most words shared, never on facts), always with the reason recorded, and never by deletion — the retired memory is struck through in the panel with a restore button. Superseded memories are filtered out of the prompt, so recall spends context only on what still holds.

Reliability, measured

tests/test_reliability.py injects seven real faults — a model that only thinks, a rate limit that never lifts, a mid-stream crash, an unsatisfiable constraint, a stall, an all-weak council, a dead primary — and scores how many were handled, where handled means recovered or reported honestly. Only hiding a fault counts as unhandled. This is the fourth axis alongside machinery, structure and substance, and it is the one a raw model has no answer to. Currently 7/7.

The hierarchy, in one line

Be useful. Be decisive. Be honest. Be recoverable. Be transparent when it matters. Honesty is the floor, not the personality — the user should not have to think about verification, only find the thing dependable. Don't lie. Don't stall. Keep moving.
